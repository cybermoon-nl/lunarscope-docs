### Request handling, in order

```rust
pub async fn scan_result(
    State(state): State<AppState>,
    headers: HeaderMap,
    body: Result<Json<ScanResultRequest>, JsonRejection>,
) -> Result<StatusCode, ApiError>
```

| # | Check | Failure |
|---|-------|---------|
| 1 | `Authorization: Bearer <key>` present and well-formed | **401** |
| 2 | `SHA-256(key)` matches an `agents.api_key_hash` → gives the agent id | **401** |
| 3 | Body is valid JSON with all required fields and a known severity | **400** (**413** if > 64 KiB) |
| 4 | `agent_id` in the body equals the agent the key belongs to | **401** |
| 5 | Text fields not empty and not too long | **400** |
| 6 | `|server time − timestamp| ≤ 60 s` | **400** |
| 7 | Insert into `scan_results` + update `agents.hostname`/`last_seen` (one transaction) | **500** |
| — | Success | **200** (empty body) |

Error answers are JSON: `{"error": "<message>"}`. A 401 also carries
`WWW-Authenticate: Bearer` (required by the HTTP standard for 401). Every
authentication failure uses the same message, *"invalid or missing API key"*,
so a caller can't tell an unknown key from a wrong agent id.

### Request body (`ScanResultRequest`)

Exactly the fields of the architecture document (5.2). It is also exactly
what `lunarscope-agent` sends (agent step 16):

| Field | Type | Rule |
|-------|------|------|
| `agent_id` | string | must be the key's agent |
| `hostname` | string | 1–255 chars |
| `scan_type` | string | 1–128 chars |
| `check_name` | string | 1–128 chars |
| `severity` | `"Critical"` \| `"High"` \| `"Medium"` \| `"Low"` \| `"Pass"` | other spellings → 400 |
| `description` | string | 1–4096 chars |
| `remediation` | string or `null` or absent | ≤ 4096 chars |
| `timestamp` | integer (Unix seconds) | within ±60 s |

Unknown extra fields are **ignored**, so a newer agent that sends an extra field
keeps working with an older master.

## Choices and justification

### API key hash: SHA-256 instead of bcrypt/argon2

The architecture document (5.3) says keys are stored hashed with "bcrypt or
argon2". This step uses **SHA-256**, on purpose:

- bcrypt/argon2 are deliberately **slow** (tens of milliseconds) and salted.
  They protect **human passwords**, which are short and guessable, so an
  attacker with a stolen database has to pay that cost per guess.
- Lunarscope's API keys are **256-bit random values** generated by the master
  (step 27; architecture 5.3: "minimum 256 bits"). Nobody can guess or brute
  force a 256-bit random value, however fast the hash is. A stolen
  `api_key_hash` column therefore doesn't reveal the keys. This is the same
  approach used for API tokens by e.g. GitHub.
- The key is checked on **every request**, and an agent sends one request per
  finding. argon2 would add its full cost to each of those, and give an
  attacker an easy way to load the CPU with garbage keys.
- An unsalted hash gives the same output for the same key, so the master can
  **look up the agent by the hash** (`WHERE api_key_hash = ?`). That is why the
  column is `UNIQUE` (step 23). With a salted hash the master would first need
  the agent id, and then the key check would depend on parsing the body.

The architecture document should be updated: "keys are stored as SHA-256
hashes; a slow password hash is not needed for 256-bit random keys".

### Authentication before the body

The `Authorization` header is checked before the body is used. The body is
taken as `Result<Json<…>, JsonRejection>`, so a broken body doesn't
automatically produce a 400 before the key is checked. An unauthenticated
caller therefore always gets 401 and learns nothing about the validation
rules. The test `authentication_is_checked_before_the_body` pins this.

### `agent_id` must match the key

Without check 4, agent A could store findings under agent B's id with its
own valid key. A mismatch is answered with **401**, because the caller isn't
authorised to report for that agent. The spec only lists 400/401, and 403
would reveal that the key itself is valid.

### Timestamp: ±60 s, not only "max 60 s old"

The guide says "max 60 s old". The architecture document (5.4) specifies
`|server_time − request_timestamp| ≤ 60`, so timestamps **in the future** are
also refused. Otherwise an attacker could pre-sign a request far in the future
and replay it later. Both server clocks are kept in sync by NTP (architecture
5.4). Replays *within* the 60 s window are not detected. That is accepted,
because TLS prevents capturing requests in the first place; nonces would
need per-agent state.

### Status codes beyond 200/400/401

- **413 Payload Too Large** for bodies over 64 KiB (`DefaultBodyLimit`). axum's
  default limit is 2 MiB. A finding is < 1 KiB, so 64 KiB leaves plenty of
  room while limiting how much a single request can make the master parse.
- **500** if the database fails (as in the architecture's table). The cause is
  logged; the response only says "could not store result".
- **405** for other methods (axum's default).
- axum's own JSON rejections (415 for a missing `Content-Type`, 422 for
  wrong types) are mapped to **400**, as the architecture document specifies
  for "the JSON is malformed".

### `hostname` and `last_seen` updated with each result

`last_seen` is in the schema "timestamp of last contact" (architecture 4.2);
the dashboard can use it to show agents that stopped reporting. The hostname
is updated too, so a renamed server shows its current name. Both updates and
the insert run in **one transaction**, so a result is never stored without
`last_seen` moving, or the other way around.

### Runtime-checked queries instead of `sqlx::query!` (decision moved from step 23)

The architecture document mentions sqlx's compile-time checked queries
(`query!`). They are **not** used:

- `query!` needs a database with the schema while compiling, either
  `DATABASE_URL` or a `.sqlx/` cache generated with `cargo sqlx prepare`
  (an extra tool, `sqlx-cli`). That cache must be regenerated and committed
  after every query or schema change, otherwise CI fails or, worse, builds
  against a stale cache.
- Instead every query is a **string literal with `?` parameters**, and the
  tests run every query against the real migrated schema (in-memory SQLite,
  same migrations as production). A typo in a column name fails `cargo test`,
  which CI runs on every push. The safety is the same, just found at test time
  instead of compile time, without the extra tooling.
- sqlx 0.9 refuses SQL that isn't a literal (step 23), so values can only go
  in through `bind`. The test `sql_in_fields_is_stored_as_plain_text` checks
  this with an injection attempt.

### Input limits

Length limits keep one agent (or a stolen key) from filling the database with
huge rows; the table has no retention (architecture 4.3). Empty strings are
refused because the dashboard can't show a nameless check.
